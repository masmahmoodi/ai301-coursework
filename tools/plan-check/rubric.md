# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause read against the repro-evidence block. Look specifically at what the repro evidence shows: control runs, error messages, artifacts, and what they rule out. | Pass when the stated cause is consistent with what the repro evidence actually demonstrates. Fail when the diagnosis blames a component or mechanism that the repro evidence (especially a control run or artifact) explicitly rules out, or when the diagnosis ignores the repro evidence entirely and asserts a cause with no support in the evidence block. Unclear counts as fail. | required |
| scope-bounded | The plan's scope statement, approach, and list of proposed changes, read as a whole. | Pass when the plan targets one bounded change that addresses the issue as stated. Fail when the plan bundles unrelated refactors, migrations, abstraction layers, multi-component rewrites, or multiple distinct problems into a single change beyond what the issue asks for. A plan that adds a CI matrix, upgrades dependencies, redesigns a code path, or campaigns on multiple fronts when the issue calls for a narrow fix fails this check. Unclear counts as fail. | required |
| executable | The plan's approach section and any files or areas named, read together. | Pass when a stranger could start building without asking the author anything: at least one specific file or code area is named, and an approach is stated (not merely "investigate" or "profile and optimize"). Fail when the plan names no concrete files or areas, when the approach is wholly open-ended ("look into it", "fix upstream or vendored, whichever"), or when the plan defers every decision to a future investigation with no target named. Unclear counts as fail. | required |
| test-decisive | The plan's test plan section, read against the repro-evidence block's steps and artifacts. | Pass when the test plan names a specific, observable outcome — something a reader could check by running a command and looking at the output (e.g. "curl returns 200 with redis=healthy", "step 3 of repro shows pushed color without leaving the view", "`zig build test` with both fuzz cases passing"). Fail when the test plan says only "things should work", "tests should pass", "it should be fast", or similar unanchored claims with no named observable. Fail also when the test plan describes only unit tests that do not exercise the behavior the repro evidence shows failing. Unclear counts as fail. | required |
| thread-aware | The plan comment read against the thread highlights block; and the repo-facts block's stated AI policy, if any. Two separate gates: (A) maintainer direction, (B) disclosure. | Gate A: Pass when the thread has no explicit maintainer direction pointing at a specific file, approach, or action. Fail when a thread highlight from an owner, member, or contributor names a specific file or code location as the culprit or posts a patched artifact requesting testing, and the plan comment ignores or contradicts that direction. Gate B: Pass when the repo-facts block states no AI disclosure requirement. Fail when repo-facts states an explicit AI disclosure requirement (e.g. "all AI usage must be disclosed") and the plan comment does not disclose AI assistance. The check fails if either gate fails. Unclear on gate A: if it is genuinely ambiguous whether a thread comment is "explicit direction" or just a hypothesis, treat it as no direction (pass). Unclear on gate B: if the AI policy wording is ambiguous, treat as no requirement (pass). | required |

## Verdict rule

Accept if every required check passes. Reject if any required check fails. There are no preferred checks. Unclear on any required check counts as fail, so a package with one unclear required check is rejected. The verdict space is binary: accept or reject only.
